# What this is?
Suppose you have an LLM and you want to make sure the output generated is safe. You want to avoid toxic statements generated by the LLM and you want to avoid leaking Personal Identifiable Information.

This project aims to create a server used to evaluate the output and determine if it is safe or not, this gate is independent of the model. It sits at the boundary and enforces policy regardless of what the LLM does internally.

A small server creates a REST endpoint that can be called to evaluate text generated by the LLM.
Two classifiers are used to evaluate the text received and then the endpoint returns a score for safety and tags for identified toxicity and/or PII classes. 

# Architecture

```
app/
  main.py              FastAPI app assembly: lifespan (loads models once at
                        startup), router registration, exception → HTTP
                        translation
  config/settings.py   Env-driven settings (SPACY_MODEL, TOXICITY_THRESHOLD)
  routers/
    check.py            POST /check — thin route handler, delegates to services
    health.py           GET /health
  services/
    toxicity.py          Classifier call, timeout + retry policy
    pii.py                presidio-based PII detection
    verdict.py            Combines toxicity + PII results into a SafetyVerdict,
                          owns request-level structured logging
  models/models.py     Pydantic request/response schemas
  logger.py            structlog config (JSON to stdout)
```

Routers stay thin on purpose — no business logic in a route handler. `verdict.py`
is the single place that decides what "safe" means (score vs. threshold, PII
flags, combined verdict), so that logic is testable without spinning up FastAPI.

## Timeout and retry behavior

The classifier call is wrapped in a 10-second timeout (`func_timeout`). If it
times out, the call is retried up to 3 attempts total (fixed 2s backoff) via
`tenacity`, and each retry beyond the first emits its own
`"Retrying due to: ..."` warning log with the attempt number — so a slow
classifier is visible in the logs as retries, not just as elevated latency.

If all 3 attempts time out, the service raises a custom `ToxicityModelTimeout`
and a FastAPI exception handler converts it into `504 Gateway Timeout` — the
service is a gateway in front of the classifier dependency, so 504 (not a bare
500) is the semantically correct response when that dependency is the thing
that failed.

# Why I built it this way

## Classifier choice
Two models were considered for toxicity: detoxify and unitary/toxic-bert

In the end detoxify was chosen because:
- detoxify returns multiple category scores (toxicity, threat, insult, obscene, etc.) — richer flags than a binary classifier
- Simpler API — no tokenizer pipeline to manage
- Supports multilingual text out of the box

For PII detection I considered using regular expressions to identify PII but in the end manual regular expressions is a poor way of detecting all the varieties of PII that can be generated, a more robust approach is to use a classifier trained to identify PII.
For this reason presidio-analyzer was chosen.
Classes of PII considered are EMAIL_ADDRESS, PHONE_NUMBER, PERSON, CREDIT_CARD, US_SSN. Two classes are excluded, LOCATION and DATE_TIME. Including this classes resulted in many innocuous texts being rejected as unsafe. For example, the text "Today is my birthday" would be classified as PII based on the DATE_TIME label.

## Why the model is pre-baked into the image
The model is included into the image to allow immediate use. You don't need to wait to download the models, you can run the service and start using the safety gate.

## Why logs go to stdout
Logs go to stdout as is standard for services running on docker.

## Design decisions

**Timeout + retry instead of a bare try/except.** A single slow classifier
call could hang a request indefinitely; a single retry-less timeout would
turn any transient slowness into an immediate 504. The tradeoff chosen here
is bounded patience: one 10s attempt, up to 2 retries, then fail loud as a
504. The cost is worst-case added latency (up to ~3x the timeout plus
backoff) on a request that was always going to fail — acceptable for a
gate sitting in front of a single dependency, not acceptable if this were
chained behind other services with their own timeouts.

**Custom exception instead of catching the library's directly.**
`func_timeout` raises `FunctionTimedOut`, which inherits from
`BaseException`, not `Exception` — FastAPI's `exception_handler` only
accepts `Exception` subclasses, so it can't be registered directly. Rather
than work around that at the FastAPI layer, `toxicity.py` catches it and
raises a local `ToxicityModelTimeout(Exception)` instead. That keeps the
HTTP-translation boundary (`main.py`) decoupled from a third-party library's
exception hierarchy, and gives a class whose meaning is specific to this
service.

**verdict.py over route-handler logic.** `check.py`'s route handler takes a
request and calls `build_verdict()` — it does not itself touch the
classifier, PII analyzer, or thresholding logic. The reasoning: route
handlers change when the transport changes (REST today, maybe something
else later); verdict logic changes when the safety policy changes. Keeping
them separate means the verdict logic is unit-testable without an HTTP
client in the loop.
